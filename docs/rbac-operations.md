# RBAC maintenance

## Sources and validation

The authoritative catalog is `functions/access-policy.js`. Generate the browser bundle and rules with `npm run generate:access`. The rule generator uses `scripts/firestore-base.rules` for schema/consent validation and replaces its legacy authorization blocks; the base file is never deployed directly.

The Access deployment source is generated by `scripts/build-access-deploy.cjs` into `functions/rbac`. Do not edit generated copies. `npm run verify:rbac` regenerates the deployment files, checks the app, runs the regression and emulator suites, and writes source-hashed activation evidence.

Use Java 21+ for emulator verification. Keep production credentials outside the repository. Both reusable skill folders under `skills/` contain task-specific implementation and validation guidance.

## Deploy and activation

Run deployments only with authorization for the target project. Preserve unrelated Firestore indexes. The active project is racepulseph.

1. Run `npm run generate:access` and `npm run verify:rbac`.
2. Preview `node scripts/migrate-access.cjs`. Set `FIREBASE_TOOLS_PATH` to the installed Firebase CLI package so the script uses its existing management connection.
3. Backfill with `node scripts/migrate-access.cjs --apply`. This preserves roles and existing custom access.
4. Deploy `firebase deploy --only functions:rbac --project racepulseph`. Set `FUNCTIONS_DISCOVERY_TIMEOUT=60` if source discovery needs more time.
5. Deploy `firebase deploy --only firestore,storage,hosting --project racepulseph`.
6. Restart the on-site Node service to load local endpoint changes without deleting its data files.
7. Activate with `node scripts/migrate-access.cjs --apply --activate`. Activation requires fresh evidence matching current sources.

The default account/email codebase is separate. Do not deploy the undeployed payments function until PayMongo secrets are configured by the owner. Its eventual deployment must retain signature validation, payment idempotency, and checkout permission checks; permission revocation must not orphan payments already accepted.

## Recovery

Access mutations are backend-only. Use a known active Super Admin and inspect history before restoring a configuration. Restoration is a new audited transaction, not deletion of earlier history. Do not edit role and access documents independently through a browser client.

The authority registry serializes Super Admin membership changes. If administrative data is damaged, an authorized project owner must repair it through management tooling after reviewing active accounts; never bypass protection by granting public writes.

For an incident, disable Access editing through the managed rollout flag while preserving audit and race data. Do not roll rules back to unrestricted role-only writes as a shortcut.

RFID pairing keys are separate device credentials. The server and station must share a unique key and configured race. Unpaired devices are rejected. Losing cloud authorization preserves captures in the operator/race queue for review and later sync; it does not authorize local anonymous writes.
